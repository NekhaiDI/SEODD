# Саморасширение тулкита

Как дорабатывать тулкит, когда пользователь просит то, чего он не умеет.
Работать только с локальной копией `seo-audit/toolkit/` (не с кэшем плагина):

```bash
[ -d seo-audit/toolkit ] || cp -R "${CLAUDE_PLUGIN_ROOT}/skills/seo-audit/scripts/" seo-audit/toolkit/
```

## Карта кода

| Файл | Отвечает за | Типовая доработка |
|---|---|---|
| `seo_kit/settings.py` | конфиг, дефолты, нормализация URL | новый параметр конфига |
| `seo_kit/crawler.py` | обход: sitemap → BFS, robots.txt, нормализация URL, порядок обхода | анализ страниц фильтров (query-параметры), поддомены |
| `seo_kit/analyzer.py` | метрики одной страницы (`analyze_page`) | новая метрика страницы |
| `seo_kit/compare.py` | агрегаты по сайту + таблица сравнения | новый агрегат, новая строка сравнения |
| `seo_kit/ai_visibility.py` | AI-боты в robots.txt, llms.txt | новый AI-бот в таблицу `AI_BOTS`, новая site-level проверка |
| `seo_kit/report.py` | HTML- и Excel-отчёты, `collect_problem_pages` | новая секция отчёта, новая колонка Excel |
| `seo.py` | CLI-команды, пайплайн `run`, чекпоинты, сводка summary JSON | новая подкоманда |

## Как устроен обход (важно при правке краулера)

`crawl_site()` — **генератор**, а не функция, возвращающая список. Он отдаёт
страницы по одной, вызывающий код (`_crawl_and_save` в `seo.py`) сразу
анализирует страницу и выбрасывает её HTML.

Так сделано не ради стиля: страницы бывают по 700 КБ, и накопление их в
списке давало гигабайты в оперативке на крупном сайте — обход без выборки
был невозможен физически. При потоковой отдаче память не зависит от числа
страниц.

Отсюда два правила при доработке:

- **Не собирать страницы в список** внутри краулера и не возвращать их
  скопом — это сводит на нет весь смысл потоковой схемы.
- **Всё, что копится по ходу обхода, должно быть ограничено размером
  сайта, а не числом запросов.** На этом уже обожглись: ссылки клались в
  очередь без проверки на дубликаты, и очередь росла как «страниц × ссылок
  на странице» — 10 392 записи всего за 7 обойденных страниц. Теперь рядом
  с `visited` живёт множество `queued`, и очередь ограничена числом
  уникальных URL сайта.

Состояние обхода (`visited`, `queue`, `sitemap_info`) краулер кладёт в
переданный ему `state` — по нему `seo.py` пишет чекпоинты и умеет
возобновлять обход (`--resume`). Если добавляете в обход новое состояние,
которое нужно пережить обрыв, — класть его туда же и сохранять в чекпоинте.

## Рецепт: новая метрика страницы

Пример — «есть ли на странице цена» (для каталога).

1. `analyzer.py` → в конец словаря `analyze_page` добавить ключ:
   ```python
   "has_price": bool(soup.find(attrs={"itemprop": "price"})
                     or re.search(r"\d[\d\s]*\s*(руб|BYN|р\.)", visible_text)),
   ```
2. `compare.py` → агрегат в `summarize_site`:
   ```python
   "pct_has_price": pct(lambda p: p.get("has_price")),
   ```
   и строка в списке `metrics` в `build_comparison`:
   ```python
   ("pct_has_price", "% страниц с ценой", "higher_better"),
   ```
3. Опционально: колонка в Excel — добавить ключ в список `columns`
   в `generate_excel_report`.
4. Проверка: `uv run seo-audit/toolkit/seo.py run --max-pages 5`.

Направления метрики: `lower_better` / `higher_better` / `neutral` —
от этого зависит зелёная подсветка «лучшего» сайта в отчётах.

## Рецепт: новая проверка в списке проблемных страниц

`report.py` → `collect_problem_pages` — добавить условие:

```python
if p.get("canonical_mismatch"):
    problems.append("canonical указывает на другой URL")
```

Список автоматически попадает и в HTML-отчёт, и в `summary_*.json`.

## Рецепт: параметры фильтров каталога (Bitrix и т.п.)

По умолчанию краулер отбрасывает все query-параметры, кроме пагинации
(`PAGEN*`, `PAGE`), чтобы не плодить дубли. Если нужно анализировать страницы
фильтров — расширить список через конфиг, без правки кода:

```bash
uv run "$SEO" config set keep_query_params "PAGEN,PAGE,arrFilter"
```

## Рецепт: новая подкоманда CLI

`seo.py`: написать функцию `cmd_<имя>(args)` и зарегистрировать её в `main()`
по образцу существующих (`sub.add_parser` → `set_defaults(func=...)`).
Пример задачи: `compare-runs` — сравнить два `summary_*.json` и показать
динамику метрик между прогонами.

## Рецепт: сложные фичи

- **Динамика между прогонами** — все прогоны уже сохраняются с таймстампами
  в `seo-audit/reports/summary_*.json`; подкоманда сравнения двух сводок
  закрывает задачу без изменения пайплайна.
- **Telegram-уведомления** — отдельный скрипт после `run`, читающий последнюю
  сводку; токен бота спросить у пользователя и хранить в конфиге.
- **Ключевые слова в title/H1/тексте** — источник данных уже есть в
  `data/*.json` (title, h1_text); анализ делать отдельной подкомандой.

## Правила

- После любой доработки — быстрый прогон `--max-pages 5` и показать
  пользователю результат до полного запуска.
- Не менять формат существующих ключей в `summary_*.json` — только добавлять
  новые (обратная совместимость с прошлыми прогонами).
- Новые поля страницы читать через `.get()` с разумным умолчанием: данные
  прошлых прогонов их не содержат, а `report` собирается и по старым файлам.
- Файлы рядом с данными называть так, чтобы они не попадали в глоб
  `data/<Сайт>_*.json`. На этом уже спотыкались: `*.meta.json` подхватывался
  как файл со страницами и сортировался после настоящего.
- Пороговые значения выносить в конфиг (`settings.DEFAULTS`), а не хардкодить.
- Стиль кода: русские комментарии, как в существующих модулях.
