# SEO-аудит и сравнение с конкурентами

Инструмент обходит сайт пользователя и сайты конкурентов, собирает SEO-метрики
каждой страницы (title, meta description, H1, объём текста, canonical, alt,
schema.org/OG, скорость ответа), сравнивает сайты между собой и формирует
HTML- и Excel-отчёты. Задача агента — запустить пайплайн, прочитать сводку и
превратить цифры в понятный план работ.

Пользователь может быть нетехническим. Не показывать ему команды и JSON без
необходимости — общаться результатами: что нашли, что чинить, где отчёты.

## Точка входа

Весь тулкит — один CLI-скрипт:

```bash
SEO="${CLAUDE_PLUGIN_ROOT}/skills/seo-audit/scripts/seo.py"
```

**Локальная копия имеет приоритет.** Если в рабочей папке существует
`seo-audit/toolkit/seo.py` (появляется после саморасширения — см. ниже),
использовать её вместо копии из плагина:

```bash
[ -f "seo-audit/toolkit/seo.py" ] && SEO="seo-audit/toolkit/seo.py"
```

Запуск — через `uv` (Python 3.11+ и зависимости ставятся автоматически из
PEP 723-заголовка):

```bash
uv run "$SEO" <команда>
```

Если uv нет — настроить окружение по разделу ниже, руками у пользователя
ничего не просить.

Все результаты пишутся в **текущую рабочую папку** пользователя:
`seo-audit.config.json`, `seo-audit/data/`, `seo-audit/reports/`.

## Окружение (самонастройка)

Пользователь может быть на macOS, Linux или Windows, и заранее у него может
не быть ничего — скилл сам определяет, чего не хватает, и ставит. Порядок:

1. **Есть uv?** (`uv --version`) → использовать `uv run`: он сам скачает
   Python нужной версии и зависимости. Предпочтительный путь на всех ОС.
2. **Нет uv → поставить:**
   - macOS: `brew install uv`; без brew —
     `curl -LsSf https://astral.sh/uv/install.sh | sh`
   - Linux: `curl -LsSf https://astral.sh/uv/install.sh | sh`
   - Windows: `winget install --id=astral-sh.uv -e`; без winget —
     `powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"`

   После установки бинарь может быть ещё не в PATH текущей сессии —
   проверить `~/.local/bin/uv` (Windows: `%USERPROFILE%\.local\bin\uv.exe`)
   и вызывать по полному пути.
3. **uv поставить не удалось** (нет прав, нет сети до astral.sh) → fallback
   на системный Python: найти интерпретатор (`python3` на unix, `py -3` или
   `python` на Windows), проверить версию. 3.10+ — ставить зависимости
   (`<python> -m pip install --user requests beautifulsoup4 lxml openpyxl`)
   и запускать `<python> "$SEO" <команда>`. Старее 3.10 — код запустится,
   но честно сообщить пользователю, что его Python устарел (EOL), и
   предложить установить свежий с python.org.

Один раз настроенное окружение не перепроверять на каждом шаге — только
при первом запуске в сессии или после ошибки запуска.

## Конфигурация: сайт и конкуренты

Конфиг создаётся и правится только командами CLI — не редактировать JSON руками.

| Просьба пользователя | Команда |
|---|---|
| первый запуск / «настрой» | `uv run "$SEO" init` |
| «мой сайт — X» | `uv run "$SEO" config set-site X` |
| «добавь конкурента X» | `uv run "$SEO" config add-competitor X` |
| «убери конкурента X» | `uv run "$SEO" config remove-competitor X` |
| «покажи, кого сравниваем» | `uv run "$SEO" config show` |
| «сканируй не больше N страниц» | `uv run "$SEO" config set max_pages_per_site N` |

URL нормализуются автоматически (`techlink.by` → `https://techlink.by/`),
дубликаты отсекаются, имя выводится из домена (можно задать `--name`).
После изменения списка — показать пользователю итоговый список сайтов.

По умолчанию конфиг настроен на кейс datastream.by с тремя конкурентами.
Если пользователь впервые запускает аудит и его сайт неизвестен — спросить
адрес сайта и конкурентов (или предложить оставить дефолт).

## Запуск аудита

```bash
uv run "$SEO" run                    # полный прогон (до 600 страниц на сайт)
uv run "$SEO" run --max-pages 50     # быстрая проверка
uv run "$SEO" run --only <имя>       # один сайт (чанковый режим)
uv run "$SEO" status                 # по каким сайтам уже есть данные
uv run "$SEO" report                 # отчёты из сохранённых данных, без краулинга
```

- Первый прогон для нового сайта делать с `--max-pages 50`, чтобы быстро
  убедиться, что всё работает, и только затем предлагать полный.
- Полный прогон занимает 5–20 минут и больше — запускать Bash с
  `run_in_background: true` и сообщить пользователю, что аудит идёт.
- Краулер уважает robots.txt и держит паузу между запросами. Не уменьшать
  `request_delay_seconds` ниже 0.3 — можно получить бан по IP на чужом сайте.

### Ограниченные окружения (чат Claude Desktop / claude.ai)

В чате скрипты выполняются в облачной песочнице, а ход ограничен лимитом
вызовов инструментов — полный прогон на 4 сайта (30–45 минут) в один ход
не помещается, и поллинг фонового процесса в цикле сжигает лимит впустую.
Правильная схема — чанками, по одному сайту за ход:

1. Первый ход: `run --only <свой сайт>` (~10 минут при 600 страницах) —
   дождаться, показать статус, **завершить ход** с фразой «напиши
   „продолжай“ — просканирую следующего конкурента».
2. Каждый следующий ход: `status` → `run --only <следующий>` → снова
   завершить ход.
3. Финальный ход: `report` — собирает сравнение и отчёты из сохранённых
   данных; если какой-то сайт так и не собрался, отчёт строится честно
   по остальным.

Не поллить фоновый процесс в цикле sleep/check — вместо этого отдавать ход
пользователю. Файлы песочницы могут не пережить долгий перерыв: если после
паузы `status` показывает «нет данных», просто пересканировать недостающие
сайты — это штатный сценарий, а не ошибка.

## Если сайт не отдался краулеру (fallback)

Сайты разные — прогон может частично не сработать. Диагностика по симптому:

| Симптом | Вероятная причина | Действие |
|---|---|---|
| 0 страниц, в консоли предупреждение | анти-бот (Cloudflare), 403/503 | проверить `curl -I <url>`; поднять `request_delay_seconds`, сменить `user_agent` через `config set`; если не помогло — собрать ключевые страницы через скилл `browser-verify` (`navigate` + `get-html`) |
| страницы есть, но `word_count` ≈ 0 | SPA: контент дорисовывает JS | подтвердить через `browser-verify` (сравнить `get-html` с серверным HTML); сообщить пользователю, что контент невидим и для AI-краулеров — это само по себе критичная находка |
| собрано подозрительно мало | sitemap неполный, ссылки за JS-меню | проверить `/sitemap.xml` вручную; поднять `max_depth`; донастроить краулер по `references/extending.md` |
| один конкурент выпал, остальные ок | частный случай выше | не блокировать весь аудит: отчёт по остальным + пометка, что сайт X недоступен краулеру и почему |

Прогон с частичными данными — валидный: честно указать в отчёте, кого и
почему не удалось просканировать.

## Интерпретация результатов

После прогона читать **только** `seo-audit/reports/summary_*.json` (компактная
сводка: сравнение сайтов, агрегаты, AI-видимость, проблемные страницы). Не
загружать в контекст `data/*.json` — там сырые данные на сотни страниц; при
необходимости точечно фильтровать их через `jq`/`grep`.

Отчёт пользователю строить по методологии из
`references/methodology.md`: краткое резюме → сравнение с конкурентами →
проблемы по серьёзности → план работ, разделённый на «быстрые победы»
(до 2 часов) и «стратегические задачи» (квартал).

**AI-видимость (GEO)**: сводка содержит блок `ai_visibility` — политика
robots.txt по AI-ботам (search/fetch/training — это разные боты!), llms.txt,
а в сравнении — доли Product/FAQ-разметки. Как интерпретировать и что
рекомендовать — `references/geo.md`. Заблокированные search-боты — критичная
проблема: сайта нет в ответах AI-ассистентов.

**Показ отчёта**: после аудита открыть HTML-отчёт пользователю, а не только
дать путь. В Claude Code: `open <путь>` (macOS) / `xdg-open` (Linux) /
`start` (Windows); если команда недоступна (headless/SSH) — просто путь.
Если в окружении есть инструмент показа файлов или артефактов (Claude
Desktop и т.п.) — использовать его.

## Дополнительные исследования

Базовый прогон — это дефолт, а не потолок. После отчёта предложить 2–3
углубления, уместных для сайта пользователя: ключевые слова и контентные
пробелы (WebSearch + собранные H1/title конкурентов), скорость и мобильная
версия (`browser-verify`), индексация (`site:домен`), присутствие в
AI-ответах. Полное меню с инструментами — в `references/methodology.md`,
раздел «Дополнительные исследования».

## Саморасширение

Когда пользователь просит то, чего тулкит не умеет (новая метрика, новая
проверка, другой формат отчёта, Telegram-уведомления, динамика между
прогонами):

1. Скопировать тулкит в рабочую папку, если ещё не скопирован:
   `cp -R "${CLAUDE_PLUGIN_ROOT}/skills/seo-audit/scripts/" seo-audit/toolkit/`
2. Дорабатывать локальную копию `seo-audit/toolkit/` — карта кода и готовые
   рецепты в `references/extending.md`.
3. Проверить доработку быстрым прогоном `--max-pages 5` и показать результат.

Кэш плагина не редактировать — изменения там стираются при обновлении.
Локальная копия автоматически подхватывается при следующих запусках (см.
«Точка входа»).

## Браузерные проверки

Краулер видит только серверный HTML. Когда нужны рендеринг, скорость или
мобильная версия — использовать скилл `browser-verify` из этого же плагина
(Chrome DevTools Protocol, без зависимостей). Типовые случаи:

- страница выглядит пустой в отчёте, но в браузере полная → SPA/JS-рендеринг;
- «проверь скорость / Core Web Vitals» → `get-performance`;
- «как выглядит на мобильном» → `emulate mobile` + `screenshot`;
- проверка микроразметки и OG на отрендеренной странице → `get-meta`.

## Ресурсы

- **`references/methodology.md`** — как превращать метрики в план работ:
  пороги, серьёзность проблем, структура отчёта, меню доп. исследований.
- **`references/geo.md`** — AI-видимость: категории AI-ботов, llms.txt,
  машиночитаемые факты, контент для цитирования, платформенные особенности.
- **`references/extending.md`** — карта кода тулкита и рецепты доработок.
- **`scripts/seo.py`** — CLI: `init`, `config ...`, `run`.
- **`scripts/seo_kit/`** — библиотека: crawler, analyzer, compare, report,
  ai_visibility.
